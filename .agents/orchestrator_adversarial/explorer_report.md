### ② CSVファイル読み込みの仕組み
* **ファイルの自動探索**: `find_single_csv(pattern_keywords, exclude_keywords)` 関数 (67行目〜) を使用。

* **操作形態**: win32com による Excel アプリケーションの COM 操作を廃止し、openpyxl による直接的な Excel ファイル編集に変更されました。

## 3. 既存の脆弱性（4選）が与える現行コードへの影響分析

既存の `adversarial_review_report.md` が指摘していた4つの深刻な脆弱性について、現在の Pandas / openpyxl 版の `run_automation.py` における影響度を評価します。

### ① Excelプロセス/ブックの解放漏れと他Excelの強制終了
* **元指摘**: win32com の解放漏れによる `EXCEL.EXE` ゾンビの蓄積、および `taskkill` による別作業中の Excel の強制終了（データ損失）。
* **現行コードへの影響**: **【完全に解消】**
  - 現在のコードでは win32com を使用せず、Excel プロセス自体を起動しない openpyxl で完結させています。そのため、ゾンビプロセスの発生自体があり得ません。
  - 起動時の `taskkill` コマンドもコードから完全に削除されているため、実行中の他の Excel ファイルを強制終了してユーザーデータを消失させるリスクも消滅しました。
  - 例外発生時には `finally` ブロックで openpyxl のワークブック（`wb_retail`）を `close()` しており、メモリリーク対策も十分です。

### ② 個人パス（kesuzuki）のハードコーディング
* **元指摘**: `error.log` の出力先絶対パスが `C:\Users\kesuzuki...` とハードコードされており、別環境で `FileNotFoundError` を起こして真のエラーを隠蔽する。
* **現行コードへの影響**: **【完全に解消】**
  - `BASE_DIR = os.path.dirname(os.path.abspath(__file__))` をベースに動的にパスを組み立てる形に修正されており、個人パスのハードコーディングはコード内から排除されました。
  - どの PC のどのフォルダにスクリプトを配置しても、配置場所の直下に `error.log` が正しく書き出されるようになっています。
  - ※ただし、検証用スクリプト `verify_all.py` には `C:\Users\kxnxg\OneDrive\デスクトップ\automation\...` がハードコードされていますが、これは検証専用であり、自動化システム本体の稼働には影響しません。

### ③ 列インデックス依存（ハードコーディング）
* **元指摘**: 列の物理順序（インデックス）を数値で直書きしているため、CSVフォーマットの小変更でクラッシュしたり、誤データをマージするサイレントバグを誘発する。
* **現行コードへの影響**: **【未解消・重大なリスクとして残留】**
  - CSVの読み込み処理では、Pandas を導入したことで `df["表記部門名1"]` や `df["商品コード"]` のように「列名」によるアクセスが可能になり、CSV側の列順序変更に対する耐性は向上しました。
  - しかし、**Excel側の操作ロジック（`step2_python_direct_merge` 内）において、依然として強烈な列インデックスのハードコーディングが多用されています。**
    - `ws_order.delete_cols(1, 3)` や `delete_cols(18, 7)`、`delete_cols(31, 7)` などの列削除位置がすべて物理数値です。
    - 店舗データや計算式の書き込み位置（`col_bulk` の E〜Q列、`col_order` の AE〜AQ列、過不足の AR〜BD列など）がすべて「削除後の特定の列位置」を前提とした固定ループで実装されています。
  - **想定されるリスク**:
    - 元の `出荷予定振分.csv` の列構成（列の追加・削除・並び順）が少しでも変わると、`delete_cols` で消される列がズレてしまい、必要な商品情報や店舗情報が消失します。
    - 計算式（過不足 = BULK - ORDER）のセル参照先がズレることで、全く無関係な列の引き算を行ってしまい、**システムがエラーを吐くことなく（サイレントバグ）、誤った出荷予定数を算出して完了する**という最も恐ろしい実務トラブルを引き起こします。

### ④ 1セル書き込みのボトルネック
* **元指摘**: win32com で 1セルずつ書き込んでおり、データ量増加でフリーズやタイムアウトを引き起こす。
* **現行コードへの影響**: **【部分解消・新たな懸念が存在】**
  - COM（win32com）経由ではないため、1セル書き込みの処理速度は劇的に向上しています。数千行のデータであっても数秒〜数十秒程度で処理できます。
  - しかし、依然として **1セルずつ代入するネストされたループ処理** で実装されており、特に以下の不要セルクリア処理で顕著な非効率さが見られます：
    - `ws_retail` の AW1:BY10000 をクリアする処理 (203〜206行目): 10,000行 × 29列 ＝ **290,000回** のループ
    - `ws_order` の AR1:BA10000 をクリアする処理 (261〜264行目): 10,000行 × 10列 ＝ **100,000回** のループ
  - これらだけで合計**39万回**におよぶセルの生成と個別値代入（`None`）が実行されており、処理実行時に数秒〜数十秒間の無駄なCPU負荷（ハングアップ状態）を引き起こしています。
  - openpyxl には、行・列を一括削除・クリアするメソッドや、DataFrame を一括書き込みするユーティリティ（`dataframe_to_rows`）が存在するため、このループ処理は極めて非効率であり、パフォーマンスのボトルネックとして現在も残留しています。

## 4. 総括と推奨される改善方針

現在の `run_automation.py` は、過去の win32com 依存から脱却したことで、「プロセスの解放漏れによる PC 動作遅延」や「個人パス依存による他環境でのクラッシュ」は完全に解消されました。

しかし、依然として以下の2つの課題が、システムの堅牢性を揺るがす「地雷」として残されています。

1. **Excel列構成の物理インデックス依存（サイレントバグの危険）**:
   - `delete_cols` による固定削除と、E〜Q、AE〜AQといった固定のセル参照による集計ロジックは、CSVフォーマットのわずかな変更で集計結果を壊します。
   - **改善策**: 列の物理インデックスをハードコードするのではなく、シート上の「ヘッダー名」をループで走査し、動的に対象列（例: "ZOZO", "名古屋"など）の列番号を取得する設計に修正すべきです。
2. **無駄な数十万回セルクリア・書き込みループ（パフォーマンス低下）**:
   - 10,000行にわたるクリア処理やセルごとの書き込みは、openpyxl のパフォーマンスを大きく低下させます。
   - **改善策**: 行や列の一括クリア（`delete_rows`/`delete_cols` の適切な範囲指定）を使用し、DataFrame からの書き込みには一括処理を導入することで、処理速度をミリ秒単位に高速化できます。
