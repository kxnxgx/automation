# 出荷明細作成 自動化スクリプト 引継ぎ資料

## 1. プロジェクト概要
- **目的**: 毎日の出荷予定振分、および各チャネル（直営店、ZOZO、OIOI、EC）の売上実績データを統合し、Excelマクロを自動実行する業務の完全自動化。
- **実行環境**: Windows, Python 3.14 (win32comを利用したExcel自動操作)
- **主要ファイル**:
  - `run_automation.py`: メインの自動化Pythonスクリプト
  - `実行.bat`: ユーザーがダブルクリックで実行するためのバッチファイル
  - `★RETAIL_CSV2計算式.xlsm`: 処理の要となるExcelテンプレート（ピボットテーブルと集計マクロを含む）
  - `input/`: 入力元となる各種CSVファイルを配置するフォルダ

## 2. 現在の進捗状況
Pythonスクリプトによる**手順1〜手順6までの一連の実装および、売上データの精確な補正処理（tennen除外・二重計上防止・在庫不足時の売上ゼロ化）の適用と検証が完了**しています。
検証スクリプト `verify_all.py` を用いたテストにより、全ての店舗・チャネルで手動で処理された本番結果の数値と完全に一致（`[OK]`）することを確認済みです。

1. **[手順1]** `出荷予定振分.csv` をExcelで開き、`RETAIL.csv` として保存（シート名も「RETAIL」に変更）。
2. **[手順2] 店舗売上**: `営業日付別売上分析.csv` から `FRV` 関連を抽出し、`営業日付別売上分析 貼り付け` シートへ値のみ貼り付け → ピボット更新。
3. **[手順3] ZOZO**: `卸売上明細.csv` (ZOZO分) から抽出し、`ZOZOOIOI` シートのB1へ貼り付け → ピボット更新。
4. **[手順4] OIOI**: `卸売上明細 (1).csv` (OIOI分) から抽出し、`ZOZOOIOI` シートのP1へ貼り付け → ピボット更新。
5. **[手順5] EC**: `order_*.csv` から指定列を抽出し、`EC_ORDER` シートへ貼り付け → ピボット更新。

## 3. 解決済みの重要バグ・特記事項（レビューアへの共有事項）

引継ぎ先でコードを改修する際、**以下のExcelテンプレートの特殊な仕様に細心の注意を払ってください。**

### ① ピボットテーブルのフィールド名仕様（超重要）
- **事象**: PythonからCSVの「ヘッダ（列名）」をExcelの1行目に書き込むと、ピボットテーブルの設定が飛んでしまい（フィールド選択が全解除される）、数値が集計されなくなるバグが発生しました。
- **原因**: テンプレート（`★RETAIL_CSV2計算式.xlsm`）内の各ピボットテーブルは、本来のヘッダ（「商品コード」「店舗名」など）ではなく、**「過去のデータ行の1行目の値（例：`23510031X` や `FJALLRAVEN STORE 名古屋ファッションワン`）」をそのままフィールド名として記憶**して構築されています。
- **対応**: 手作業のコピペ（可視セルのコピーによりヘッダが除外されていた）を完全再現するため、`run_automation.py` の `write_df_to_sheet` 関数では**意図的にヘッダを書き込まず、データ行のみをそのまま上書き**する仕様にしています。

### ② VBAマクロ実行時のシート名認識エラー
- **事象**: 手順6のマクロ実行時、「インデックスが有効範囲にありません（エラー9）」で停止。
- **原因**: VBA側が `RETAIL.csv` ブック内の `RETAIL` というシート名をハードコードで指定して探しにいっていましたが、CSVを「名前を付けて保存」しただけではシート名が元の `出荷予定振分` のままになっていました。
- **対応**: Python側の手順1で、SaveAs直後に `ActiveSheet.Name = "RETAIL"` として明示的にシート名を変更する処理を追加しました。

### ③ ピボット総計の #N/A エラーによるクラッシュ
- **事象**: ピボット更新後、Python側で「貼り付けたデータの合計値」と「ピボットの総計」を突合する検証ロジックにて、`could not convert string to float: '#N/A'` エラーが発生して異常終了。
- **対応**: 突合ロジック内の `float()` 変換を独自関数 `safe_float()` に置き換え、および文字列が含まれる場合は検証をスキップするように安全対策を施しました。

### ④ tennen ブランド製品の自動除外
- **事象**: tennenブランドの商品は別の専用ツールで処理する必要があるため、今回の自動化対象から排除する必要があります。
- **対応**: 商品コードが `TNF`, `TNP`, `TNT` から始まるもの、および表記部門名やブランド名が `TENNEN` の商品について、すべての集計処理から自動で除外する判定処理 `is_tennen` を実装しました。また、新規に検知されたコード（leaked_codes）からも同様に除外されます。

### ⑤ TOKYO店の二重計上防止
- **事象**: 「TOKYO」で店舗検索を行う際、「FJALLRAVEN by 3NITY TOKYO NODE」店舗の売上データが部分一致により二重計上されるバグが発生しました。
- **対応**: TOKYO店の集計処理において「NODE」という文字列を含まない列のみを対象とするように修正しました。

### ⑥ 在庫不足品の自動売上ゼロ化（誤発注防止）
- **事象**: A列（過不足残 < 0 で赤）になっており、かつC列（NWA）とD列（RETAIL確保）の在庫数値がともに0の場合、出荷不能であるため売上数を `0` にする必要があります。
- **対応**: 既存商品の売上書き込み時、および検証スクリプトにおいて、「C列=0 かつ D列=0 かつ 確保枠合計 < 売上合計」の条件を満たす場合に、売上数を自動的にすべて `0` に上書きするロジックを実装しました。また、元データ（order）に登録されていない新規商品については在庫数が0（不足）となるため、新規行の自動追加を行わない仕様としました。これにより、手動での売上ゼロ化と同等の精確な仕分けを自動で行えます（名古屋の売上合計が本番同様の44点になることを確認済みです）。
